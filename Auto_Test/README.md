# Сравнение Selenium WebDriver и Selenide

В данном анализе сравниваются два подхода к автоматизации тестирования на примере базового сценария 
авторизации на тестовом стенде SauceDemo.

## Сравнительная таблица

| Критерий | Чистый Selenium WebDriver | Selenide |
| :--- | :--- | :--- |
| **Объем бойлерплейта** | **Высокий**. <br/>Требуется вручную прописывать конфигурацию драйвера (`ChromeDriver`), управлять его сессией (`driver.quit()`), а также для каждого нестабильного шага создавать инстанс `WebDriverWait` с указанием `ExpectedConditions`. | **Минимальный**. <br/>Открытие браузера, управление сессией, закрытие окон и создание скриншотов при падении происходят под капотом автоматически. Код сфокусирован только на бизнес-логике шагов. |
| **Читаемость ассертов** | **Низкая / Средняя**. <br/>Ассерты разделены на техническую проверку состояния элемента и стандартные утверждения тестового фреймворка (например, `assertTrue(element.isDisplayed())`). Сообщения об ошибках малоинформативны без кастомного текста. | **Высокая**. <br/>Используется человекочитаемый DSL-стиль (`element.shouldBe(visible)`). В случае падения Selenide выдает подробный отчет: что искали, сколько ждали, состояние DOM и скриншот. |
| **Решение проблемы "протухания" DOM (StaleElementReferenceException)** | **Ручное**. <br/>Если страница обновляется по AJAX/JS, старая ссылка на элемент в памяти "протухает". Тестировщик вынужден вручную перехватывать исключение, делать повторный поиск `findElement` или оборачивать вызовы в `wait.until(...)`. | **Автоматическое (Умное)**. <br/>Selenide решает проблему динамического DOM с помощью концепции **"ленивого поиска" (Lazy Evaluation)**. Элемент не ищется в момент объявления, а обертка `SelenideElement` осуществляет повторный поиск элемента на странице прямо в момент совершения действия (`click`, `setValue`, `shouldBe`), если старый элемент исчез. |

## Как Selenide решает проблему динамического (протухающего) DOM

Главное архитектурное отличие Selenide от Selenium в работе с нестабильным DOM-деревом 
(AJAX, React/Vue/Angular подгрузки) заключается в том, что Selenide **автоматически перезапрашивает 
элемент из DOM**, если тот изменился или временно пропал.

Когда вы вызываете метод (например, `$("#login-button").click()`), Selenide запускает цикл ожидания 
(по умолчанию 4 секунды). Если в этот момент браузер перерисовывает страницу и падает `StaleElementReferenceException`, 
Selenide не роняет тест. Он мгновенно находит элемент на странице заново по селектору и повторяет действие. 
Тестировщику больше не нужно писать громоздкие циклы или расставлять `ExpectedConditions` перед каждым кликом.






# Автоматизация тестирования учебного стенда Swag Labs (SauceDemo)

Проект представляет собой учебный фреймворк для автоматизации сквозного (End-to-End) тестирования веб-приложения [SauceDemo](https://saucedemo.com) с использованием стека **Java + Maven + JUnit 5**.

В рамках проекта реализованы два подхода к автоматизации: на чистом **Selenium WebDriver** и на современном фреймворке **Selenide**, а также применена многоуровневая архитектура.

---

## 🛠 Технологический стек

* **Язык программирования:** Java 17
* **Сборщик проектов:** Maven
* **Тестовый фреймворк:** JUnit 5 (Jupiter)
* **Инструменты автоматизации:** Selenium WebDriver (4.17.0) / Selenide (7.16.2)
* **Управление конфигурацией:** Кастомный `ConfigReader` для файлов свойств (`.properties`)

---

## 📐 Архитектура проекта (Слойность)

Фреймворк спроектирован по принципу разделения ответственности с использованием паттерна **Page Object + Steps**. Это минимизирует дублирование кода, изолирует локаторы от логики и делает тесты легко читаемыми:

1. **Слой конфигурации и утилит (`utils` / `resources`)**
    * Все тестовые данные (URL, логин, пароль) изолированы в файле конфигурации `saucedemo.properties`.
    * Класс `ConfigReader` обеспечивает динамическую и потокобезопасную подгрузку параметров в тесты.
2. **Слой страниц (`pages`)**
    * Содержит только описание локаторов (`SelenideElement`) и атомарные низкоуровневые действия над ними (ввод текста `setValue`, клик `click`).
    * **Важно:** Этот слой не содержит никаких бизнес-проверок (assert'ов) и комплексных цепочек шагов.
3. **Слой шагов (`steps`)**
    * Объединяет атомарные действия страниц в законченные высокоуровневые бизнес-сценарии (например, `login`, `addTwoItemsToCartAndGoToCart`, `fillCheckoutDataAndFinish`).
4. **Слой тестов (`tests` / `baseTest`)**
    * Базовые классы (`BaseTest`) управляют глобальными настройками браузера.
    * Тестовые классы выполняют исключительно роль оркестраторов: они вызывают цепочки шагов из слоя `steps` и содержат финальные бизнес-проверки.

## 📊 Аналитическая часть: Сравнение Selenium и Selenide

Ниже приведена сравнительная таблица инструментов по ключевым критериям на основе реализованных сценариев авторизации и сквозной покупки.

| Критерий сравнения | Чистый Selenium WebDriver | Selenide |
| :--- | :--- | :--- |
| **Объем бойлерплейта (рутинного кода)** | **Высокий**. Требуется вручную инициализировать драйвер, настраивать параметры окон, следить за закрытием сессий (`driver.quit()`), а также для каждого нестабильного шага вручную объявлять `WebDriverWait` и прописывать условия `ExpectedConditions`. | **Минимальный**. Жизненный цикл браузера, скачивание бинарников (через встроенный WebDriverManager), очистка кэша и закрытие окон происходят автоматически «под капотом». Код сфокусирован только на шагах теста. |
| **Читаемость ассертов** | **Низкая / Средняя**. Проверки разделены на техническое извлечение состояния элемента из DOM и стандартные утверждения JUnit (`assertTrue(element.isDisplayed())`). Сообщения об ошибках малоинформативны без кастомного текста. | **Высокая**. Используется лаконичный человекочитаемый DSL-стиль (`element.shouldBe(visible)`). При падении выводится детальный отчет: какой селектор искали, сколько секунд ждали, скриншот и снимок DOM. |
| **Решение проблемы "протухания" DOM (StaleElementReferenceException)** | **Ручное**. Если страница обновляется по AJAX/JS, ссылка на элемент в памяти устаревает. Тестировщик вынужден вручную перехватывать исключение, делать повторный поиск `findElement` или оборачивать вызовы в тяжелые циклы ожидания. | **Автоматическое (Умное)**. Selenide решает проблему динамического DOM с помощью концепции **«ленивого поиска» (Lazy Evaluation)**. Поиск элемента запускается не в момент его объявления, а непосредственно в секунду выполнения действия (`click`, `setValue`, `shouldBe`). При возникновении ошибки `StaleElementReferenceException` Selenide автоматически перезапрашивает элемент из DOM-дерева заново в пределах установленного таймаута без явных указаний со стороны инженера. |

## 🚀 Как запустить тесты

Вы можете запустить тесты через терминал с помощью стандартных команд Maven:

```bash
# Очистить прошлые сборки и запустить все тесты
mvn clean test
```
